# Engage (working name)

A multi-tenant employee engagement platform. It covers community recognition with points, local and industry news, games with live presence, chat, and employee profiles. Our client resells it to customer companies.

- What we're building and the open questions: [docs/scope.md](docs/scope.md)
- Similar products: [docs/competitors.md](docs/competitors.md)

## Stack

| Part | Tech |
|---|---|
| Monorepo | pnpm workspaces + Turborepo |
| Web | Next.js 16 (App Router), React 19, Tailwind CSS 4 |
| API | NestJS 12 (ESM), REST under `/api`, Socket.IO for realtime |
| Database | PostgreSQL 17 + Prisma 7 (`@prisma/adapter-pg`) |
| Cache / presence | Redis 7 (wired in docker-compose; app integration pending) |

## Layout

```
apps/
  web/        Next.js portal. Sidebar filtered by role and plan; module pages
  api/        NestJS API. Auth guard, tenancy, modules, realtime gateway
packages/
  shared/     Roles + permissions, plan features, realtime event contracts
  db/         Prisma schema, generated client, createPrismaClient()
docs/         Scope, open questions, competitor research
```

## Getting started

Requires Node 22+, pnpm 10 and Docker.

```bash
pnpm install
cp .env.example .env
pnpm infra:up                 # Postgres + Redis
pnpm db:migrate               # create tables
pnpm dev                      # web on :3000, api on :4000
```

Other commands: `pnpm build`, `pnpm typecheck`, `pnpm lint`, `pnpm db:studio`,
`pnpm --filter @platform/api test` and `test:e2e`.

### Client demo (web only)

The web app currently runs as a self-contained demo. No API or database is needed:

```bash
pnpm --filter @platform/web dev
```

Open http://localhost:3000. The login page has one-click demo accounts for each role:
Employee, Manager, HR, Company admin and Reseller. The demo data
(`apps/web/src/lib/demo/seed.ts`) is fictional and is saved in the browser, so
changes survive a refresh. Use **Reset demo data** in the account menu to start over.

Every demo action lives in `apps/web/src/lib/demo/store.tsx`. Each one maps to an API
endpoint, so swapping the demo for real data is a change in that one file.

| Area | Pages |
|---|---|
| Sign-in | `/login`, `/signup` (two-step company trial), `/forgot-password` |
| Employee | `/home` (HR's note, poll of the day), `/lounge` (posts, polls, automatic praise messages), `/cohort` (topic cohorts + recognition wall), `/cohort/[id]`, `/news` (Current Affairs: local + 10 industries), `/games` (quiz, chess, sudoku, tic-tac-toe), `/chat`, `/directory`, `/assessments` (psychometric), `/profile` (photo/avatar, tasks), `/people/[id]` |
| Manager | `/team`, team view in `/assessments` |
| HR | `/people`, `/insights`, `/hr-toolkit` (question bank + PDF), company view in `/assessments` |
| Company admin | `/admin` (branding, modules, games on/off, praise points, news industries, audit log) |
| Reseller / platform | `/console` (customers), `/console/cohorts` (platform-wide cohorts), `/console/plans` |

Praise points depend on who receives it: 5 for a colleague, 10 for a manager, 15 for the MD
(each company can change these in Company admin). The HR question bank PDF is generated by
`python3 apps/web/scripts/build-hr-question-bank.py`.

### Supabase

The Supabase project URL and publishable key go in `apps/web/.env.local` and the root
`.env`. Both files are git-ignored. To point Prisma at Supabase Postgres, set
`DATABASE_URL` (pooled, port 6543) and `DIRECT_URL` (port 5432). Both strings are in
Supabase under Project Settings → Database.

### Signing in during development (API)

Real sign-in is not built yet (the SSO provider is still to be chosen). Until then:

- **API:** send `x-dev-user-id: <user id>` on requests.
- **Socket:** connect with `auth: { devUserId: "<user id>" }`.
Both are switched off when `NODE_ENV=production`.

## How multi-tenancy works

- Every tenant-owned table has a `tenantId`. Every service query filters by the signed-in user's `tenantId`.
- The tenant's **plan** lists which modules are on. `@RequireFeature('chat')` blocks a module that isn't in the plan.
- Roles are checked with `@RequirePermission(...)`, using the `PERMISSIONS` table in `packages/shared`. The web app uses the same table to decide what to show.
- Profile details come in two levels. Colleagues see public fields. The person, their manager, HR and the admin also see employment details.

## API surface (so far)

| Method | Path | Notes |
|---|---|---|
| GET | `/api/health` | Public |
| GET | `/api/cohort/feed` | Praise feed, cursor-paginated |
| POST | `/api/cohort/praise` | Gives points via the ledger |
| GET | `/api/profiles/me`, `/api/profiles/:id` | Detail level depends on role |
| GET | `/api/people` | Managers: own teams. HR and admin: everyone |
| GET | `/api/news?category=LOCAL\|SECTOR` | Reads cached articles |
| GET/POST | `/api/chat/conversations` | Direct chats are reused |
| GET | `/api/chat/conversations/:id/messages` | |
| GET | `/api/games/catalog` | |
| POST | `/api/games/sessions`, `/api/games/sessions/:id/respond` | Pushes invites over the socket |

Socket events are listed in `packages/shared/src/realtime.ts`.
